### 新增 /Users/wanghui/Code/mac-cleanup-skill/disk-8020.sh
复刻其下钻逻辑：`du -xk` 单遍全量 dump → awk 重建父子关系 → 自顶向下每层按大小降序，
累计到 80% 的分支继续深入，其余折叠一行。参数：阈值 / 最小MB / 最大深度 / 每层上限 / 降噪%。
根层特例：不受 80% 约束，高于降噪下限的顶层分支全部展开（否则 private 9.3GB 会被折叠）。

### awk 递归的老坑（踩了两次）
BWK awk 中函数的"局部变量"只能靠**多余形参**声明。漏声明即全局，
递归返回后会用子调用的值覆盖父层的 `show` / `show_direct`：
- `show_direct` 缺失 → 父层误打印 `<直属文件>`
- `show` 缺失 → 父层循环上界被子调用改写，兄弟节点直接消失
规则：递归函数里**每一个**临时变量（含布尔标记、循环上界）都必须列入形参。

## 调研：应用安装历史 / 目录审计 / 缓存 / 孤儿残留（产出 docs/app-audit-research.md）

### 结论
macOS 无安装数据库、无卸载契约。成熟范式 = 多源证据 → bundle id 归因 → **声明减法** → 回收站优先。
`ORPHAN_RULES` 现用「/Applications 名字子串」是弱判据，误判与漏判并存，建议 v1.4 拆出只读 `app-orphans` 模块。

### 本机实测（macOS 26.1）关键数字
- `lsregister -dump`：797 条 bundle 记录 / 23MB / **3.1s**；其中 **338 条 fnfErr（磁盘上已不存在）**，69 个唯一 id，60 个全盘无同名现存 bundle
- 与 Library 路径交叉：13 个 id 命中，≈2.14GB；最大 `com.tencent.WeWorkMac` **1864MB**（应用已删，容器 + 4 个 Group Container 仍在）
- `cn.trae.solo.app` 的 LS 记录指向 `~/.Trash/TRAE SOLO CN.app` —— 废纸篓里的直接证据
- **反例**：`~/Library/Containers` 717 个 vs 顶层已安装 bundle id 237 个 → 朴素差集 651 个"孤儿"，绝大多数是 com.apple.* 代理 / IPCHelper / widget / UUID 容器。**用顶层 .app 做声明集会产出 ~96% 假阳性**
- `SPApplicationsDataType -json` 有 obtained_from / lastModified / signed_by，**无安装日期、无最后使用**
- QuarantineEventsV2 本机仅 7 行，且 URL 列常空 → 不可靠
- knowledgeC.db 无 sudo/FDA 读不到（Operation not permitted）

### 平台事实（写脚本时要用）
- **macOS 26 已移除 `lsregister -kill`**；只剩 `-dump`（只读）、`-gc`、`-delete`（需重启且会被重建）、`-u`
- `/private/var/log/install.log` 存在（2.3MB）；`pkgutil --pkgs` 114 条；MAS 应用 12 个；brew cask 7 个
- `eslogger` / `fs_usage` / `opensnoop` 均在 `/usr/bin`，可用于给单个 App 追踪真实写入路径

### 待办（未实现）
v1.4 `app-orphans` 只读审计：声明集 = LS 存活记录 ∪ SPApplications ∪ 全部 .app 内嵌 Info.plist ∪ 运行进程 ∪ com.apple.*；
置信度 A/B/C 分级；**声明集不完整时输出零结果**；报告 TSV → 人工复核 → 再走 `safe_remove`。
